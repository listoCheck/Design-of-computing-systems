# Лабораторная работа № 4: FreeRTOS, вариант 1 «Часы»

Проект для SDK-1.1MC.427 повторяет функции лабораторной № 3: часы MCP79411,
OLED-дисплей и совместимый клиент ПК по UART. Используются две задачи FreeRTOS:
`display` обновляет OLED, `clock-uart` обслуживает часы и команды клиента.
USART6 работает по прерываниям. Данные часов передаются в задачу дисплея через
очередь длиной один элемент; общая шина I²C защищена мьютексом.

## Что сделать в STM32CubeIDE

1. `File → Import → General → Existing Projects into Workspace`.
2. В `Select root directory` выбрать папку `C:\Users\admin\Design-of-computing-systems\lab4`,
   отметить `lab4`, отключить `Copy projects into workspace`, нажать `Finish`.
3. Выделить проект и выполнить `Project → Build Project` (`Ctrl+B`).
   Файл прошивки: `lab4/Debug/lab4.elf`.
4. Подключить питание стенда и разъём **DBG USB**. Встроенный программатор
   работает через FTDI/JTAG и `SDK11M.cfg`. При первом подключении нужен WinUSB
   для `SDK 1.1M Debugger (Interface 0)`; Interface 1 — отдельный UART-канал.
5. Скомпилированную прошивку можно загрузить из PowerShell в корне репозитория:

   ```powershell
   python lab1/tools/board.py probe
   python lab1/tools/board.py flash --elf lab4/Debug/lab4.elf
   ```

   После `verify` стенд перезапускается. Скрипт из `lab1` использует тот же
   FTDI/JTAG и совместимый конфигурационный файл; прошивается именно ELF lab4.
   Можно также создать отладочную конфигурацию OpenOCD в CubeIDE с
   пользовательским `lab4/SDK11M.cfg`; стандартная конфигурация ST-LINK
   для встроенного FTDI-программатора не подходит.

6. Узнать номер COM-порта интерфейса UART и запустить графический клиент из
   лабораторной 3:

   ```powershell
   python -m pip install --target lab3/build/python-deps -r lab3/client/requirements.txt
   python lab3/client/app.py COM5
   ```

   Заменить `COM5` фактическим номером. Клиент отправляет PING и ожидает PONG,
   показывает время/дату/день недели и позволяет установить новые значения.
   Лог находится в `lab3/logs`. Режим `DEMO` является симуляцией клиента и не
   подтверждает работу устройства. Для COM может потребоваться отдельный
   драйвер FTDI VCP для Interface 1.

## Проверка 20 кадров в секунду

В правом верхнем углу OLED отображается счётчик `00…99`; он меняется после
каждой успешно переданной полной картинки. Плановый период начала кадра 40 мс
(25 кадров/с), что оставляет запас относительно 20 кадров/с. Страница размером
128 байт отправляется целиком; затем задача отдаёт процессор на один тик, чтобы
обработка UART и часов продолжалась между страницами. Передача всех восьми
страниц и ожидание мьютекса входят в измерение времени кадра.

В CubeIDE в `Expressions` добавить `display_stats` и `lab4_fault`. Измерять
после старта, без длительных остановок на breakpoint:

- `completed` — число успешно записанных полных кадров;
- `fps_last` — целая частота в последнем окне не короче 1 секунды;
- `fps_min` — минимум таких окон с момента старта, включая начальное окно;
- `max_gap_ms` — максимальный интервал между завершениями кадров;
- `missed` — число интервалов более 50 мс; `failed` — ошибки передачи;
- `max_transfer_ms` — максимальное время обработки и передачи кадра.

При ошибке OLED `fps_last` и `fps_min` становятся нулём, `failed` растёт.
Проверить за несколько минут и во время повторных PING/GET/SET: экран и счётчик
двигаются, часы и клиент отвечают, `fps_last >= 20`, `failed == 0`,
`lab4_fault == 0`. `max_gap_ms`/`missed` дополнительно показывают короткие
задержки, которые средняя частота может скрыть. Для формального подтверждения
стабильных 20 кадров/с сохранить результаты измерений на реальном стенде;
при отключённом или неисправном OLED гарантия обновления физически невозможна.
До проверки аппаратуры частота 25 Гц остаётся плановой, не измеренной.

## Сборка и тесты из командной строки

```powershell
python lab4/tools/build.py
python lab4/tests/run_tests.py
python -m unittest discover -s lab3/tests -p test_client.py -v
```

Для тестов ARM нужен пакет `unicorn`, для клиента — `pyserial`. Тесты RTC,
протокола, графического буфера и статистики используют моделируемую шину;
они не проверяют реальную задержку OLED и планирование на микроконтроллере.
Сборка проверена также штатной сборкой CubeIDE.
